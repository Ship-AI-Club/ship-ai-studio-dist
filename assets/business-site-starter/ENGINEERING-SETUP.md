# Engineering setup

Model precedence comes from setup.modelPrecedence in the Studio role registry; apply it with `scripts/model-setup.mjs` in the Studio plugin. If the shared brief already saves setup.siteBuildModel, use it and ask nothing. Only if none is saved, the PM asks the owner exactly once: “Which model should build your website? Opus 5.5 Medium is the default: it uses more tokens and can improve output. Sonnet 5.5 Medium is more conservative with tokens. Quality varies.” Save the answer, or the default claude-opus-5-5 if the owner has no preference, as setup.siteBuildModel with setup.siteBuildEffort medium and setup.siteBuildFast false. That choice drives website implementation only. Marketing creative production always uses setup.creativeBuildModel claude-sonnet-5-5 with setup.creativeBuildEffort medium and no fast field, independent of the site choice; picking Opus for the site never changes creative, and creative is never upgraded or switched silently. Keep this separate from business.pricing.model. Other bots read this choice and never ask it again. If no PM or saved choice exists, ask once and save the answer before implementation. This choice configures the coding handoff, not an unsupported claim that a native bot model changed. Verify available model IDs and the actual Cloud selector. If the selected model is unavailable, show the available alternatives and get a decision. Never silently substitute, upgrade or fall back to another model or budget.

Before project work, verify PStack is installed, then install the published product team plugin from its real catalog entry. Templates must include both supported plugin integrations when available. Verify installed, enabled and tool-ready states separately for each bot. A link, prompt, native skill-card count or local Cursor install is not proof of Grok plugin loading. Resolve IDs from the actual catalog; never invent them. Do not report ready if the product team plugin is not published, accessible or enabled. Preserve existing account connections; recipients use their own logins. No credentials, private chats or client facts belong in exports. Run the actual /setup-pstack workflow and inspect its model/budget rules. Preserve the shared model choice and scope configuration to this project. Then run the plugin's setup skill and full file audit. All five roles use the same pinned plugin release and source manifest. Read relevant full skill files and references before work; do not paste every skill into each prompt. Keep presence/integrity evidence separate from read/application evidence. Use the role map to select applicable skills. Keep full profile.description and the getting-started entrypoint in each export. Do not add unrelated plugins or recurring routines from reference bots.

Use the verified PStack and product team plugin setup before implementation. Cursor Cloud delegation is a built-in capability, not a similarly named plugin. Check team policy if it is missing. Use GitHub only when the selected repository needs it and verify actual access. When a real repository exists, run /create-verification-skill if no suitable verify-* skill exists. Reuse an existing project verifier where available. Do not delete shared private skills to free a slot. Keep complete skills, references, licenses and verification scripts in the source kit and actual Cloud workspace. A Cloud agent already in the assigned run implements there and must not launch a nested run. Record sourceBriefVersion and sourceBriefSha256 from the current PM brief. Map its facts and approval state into site and API contracts without changing their shapes. Do not compare schemaVersion to a content version. Before any push or deployment trigger, run the repository typecheck where applicable, targeted tests and production build on that commit. Record exact commands and exit codes; never use hosting CI as the first compiler. Stop only for a required login, terms or access decision; keep secrets out of chat and exports.
